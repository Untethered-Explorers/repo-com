# repo-com 0.1.0 — unreleased source snapshot

**Workspace/package version:** `0.1.0`

**Source snapshot:** 2026-09-25 (`HEAD 8dd506c`)

`Cargo.toml`, the workspace package manifests, and `dist-workspace.toml` agree
on `0.1.0`. The Product Vision records `1.0` as a planned product target. The

This file is a versioned source-snapshot record, not a claim that `0.1.0` has
been published or approved.

## Summary

The source snapshot contains a composed Rust 2024 workspace with 31 packages
and a final `repo-com` executable target. It covers secret-free repository
configuration, local repository-scoped SQLite state, immutable drafts, exact
human approval or policy authority, dedicated-bot Discord REST v10 setup and
message operations, local delivery claims, untrusted inbound retrieval, reply
drafts, audit evidence, lifecycle inspection, retention, and confirmed local
purge.

The executable can be built from the checkout. The repository does not contain
a public installer, a published release archive, or a release tag. Automated
Discord coverage uses token-free WireMock fixtures and a complete mocked
journey; it does not establish live Discord behavior or human acceptance.

## Highlights

- Final `repo-com` process routing with `config`, `policy`, `draft`, `send`,
  `setup-check`, `inbox`, `reply`, `audit`, `state`/`lifecycle`, and `purge`
  command groups.
- Strict protocol version 1 JSON on stdin, exactly one machine JSON object on
  stdout, separated diagnostics on stderr, explicit identifiers, and no default
  destination.
- Schema-version-1 `.repo-com.toml` with named destination, mention, and
  inbound aliases, exact auto-send tuples, SHA-256 configuration hashes, and
  strict rejection of unknown or secret-like fields.
- Repository-scoped SQLite state with forward migration 1, WAL, foreign keys,
  a bounded busy timeout, immutable local evidence triggers, Unix user-only
  modes, and the inherited Windows profile ACL boundary.
- Immutable draft revisions, deterministic Discord text and nonce rendering,
  allowlisted mentions, pre-send secret-pattern scanning, exact-revision TTY
  approval, exact policy activation, and fail-closed eligibility.
- Dedicated-bot-only REST v10 setup checks, one-attempt message delivery,
  dynamic rate-limit classification, atomic local delivery claims, bounded
  retry/recovery contracts, and conservative unknown-delivery reconciliation.
- Bounded untrusted inbound fetch, local acknowledgement/archive markers,
  validated threaded reply drafts, redacted audit queries, read-only state and
  lifecycle inspection, retention sweeps, and deterministic local purge plans.
- Accessible labeled terminal output at an 80-column minimum, keyboard
  confirmations, `NO_COLOR`, cancellation, and non-TTY fail-closed behavior.
- Token-free mocked E2E coverage, including concurrent duplicate prevention and
  post-dispatch unknown handling; a local performance harness; and CI/release
  policies for Linux, macOS, and Windows packaging.

## Compatibility and prerequisites

- Rust `1.98.1`, edition 2024, and the committed `Cargo.lock` are pinned for
  source development.
- `cargo-nextest` is required for the documented full test command.
- Release-oriented state opens require linked SQLite `3.53.4` or newer. The
  release workflow requires a pre-provisioned static SQLite library and checks
  that release binaries do not dynamically link SQLite.
- Declared release targets are `x86_64-unknown-linux-gnu`,
  `x86_64-apple-darwin`, `aarch64-apple-darwin`, and
  `x86_64-pc-windows-msvc`.
- A Discord bot token and network access are required only when an operator
  invokes the production `setup-check`, `send`, or `inbox.fetch` path. The
  token is read only from `REPO_COM_DISCORD_TOKEN` and must be a raw dedicated
  bot token.
- There is no installed package or self-updater in this snapshot.

## Installation or upgrade

From a local checkout:

```bash
cargo build --release --locked --package command_routing_contract --bin repo-com
./target/release/repo-com --version
```

The version output is `0.1.0`. On Windows, use the corresponding `.exe` path.
The release plan configures explicit archives rather than an installer. If a
future tag workflow supplies an archive, the operator must verify its checksum,
license evidence, SBOM, and version before extracting the binary. Installation
is explicit; the product does not mutate Discord during setup and does not
self-update.

There is no packaged rollback procedure in this snapshot. Preserve the local
SQLite database and its WAL sidecars with a SQLite-aware backup procedure
before replacing a binary. Schema migrations are forward-only, and an older
binary must not be assumed to open a newer schema.

## Known limitations

- No Git tag, published archive, installer, publication, or release date is
  recorded for `0.1.0`; this is an unreleased source snapshot.
- Automated Discord evidence is token-free and WireMock-based. No live Discord
  workspace compatibility or teammate round trip is recorded here.
- Human UX/accessibility, security/privacy, live Discord, and final release
  reviews are separate pending work. Automated checks are not approval.
- The current command tree has no separate `reconcile` command, policy
  deactivation command, or retention-sweep command. An embedding application
  must use the domain service for retention and recovery.
- The final `inbox.fetch` composition supplies an empty accepted-delivery list
  to the fetcher. Direct bot mentions are handled by the current path, but a
  non-mention reply may not be retained by the CLI; this is a known correlation
  gap.
- A `send` result of `accepted` is transport evidence, not proof that a
  teammate read the message. The product provides no read receipt, response
  analytics, or current-remote-state guarantee.
- Unknown or unresolved delivery remains blocked. There is no automatic resend;
  a later attempt requires a fresh, explicit operator decision after read-only
  reconciliation.
- Local state is not encrypted at rest. User-only filesystem permissions do not
  protect against local-account compromise, readable backups, or filesystem
  snapshots. The product sends no telemetry and does not synchronize local state
  or audit evidence.
- The secret scanner is defense in depth, not complete data-loss prevention.
- Arbitrary destinations, user tokens, self-bots, automatic permission changes,
  remote message deletion, and background services are unsupported.

## Security and privacy

- Discord credentials are environment-only, bot-only, redacted, and zeroized
  where owned; no credential is written to configuration or local state.
- Configuration, drafts, inbound data, and audit diagnostics are treated as
  separate trust boundaries. Inbound content cannot grant authority.
- Local claims, immutable evidence, exact hashes, and conservative recovery
  reduce duplicate and stale-authority risk; they do not make Discord
  transport exactly-once.
- Retention and purge are local-only. The database is not encrypted at rest,
  the workspace sends no telemetry, and backups, snapshots, and local-account
  compromise remain disclosure risks.
- There is no read receipt, response analytics, user-token support, arbitrary
  destination support, or automatic unknown-delivery resend.
